# 00003 — The runtime theme check: a source-only package and the library's half

> Status: **approved 2026-10-14**. Supersedes nothing.

The theme audit reads markup. It inventories the keys a theme defines, variant by variant, and lists
the keys each of its consumers references that a theme leaves undefined. That is a model of
Avalonia's resource lookup: its `ThemeDictionaries`, its variants that inherit from others, and its
merged and included dictionaries. A model can be wrong where nothing reads it against the real
lookup. DiffView's `ThemeResolutionTests` do that reading. They switch the application's theme and
variant, ask `TryGetResource` for each key, and compare what is missing with the gaps the audit
reports. The developer decided on 2026-10-13 that this check ships from here, and on 2026-10-14 how:
what needs a running Avalonia as `.cs` files compiled into each adopting project against its own
Avalonia, and the rest in the library, so that it serves any Avalonia project while this repository
references no Avalonia in what it ships.

Here, a *consumer* is what the audit's configuration calls one: a set of markup folders it reads
references from. The *adopting project* is the test project that compiles the check in.

## What DiffView's check does today

| What | How |
|---|---|
| The application | A headless test application: Semi first in `Application.Styles`, then DiffView's own `StyleInclude` |
| The targets | For DiffView's own tokens, Fluent and Simple, each in Light and Dark, and Semi in its six variants: ten in all. For AvaloniaEdit's keys, Semi's six variants |
| A switch | `ThemeSwap` puts Fluent, Simple or Semi in `Styles[0]`, sets `RequestedThemeVariant`, and restores both |
| A lookup | `Application.Current.TryGetResource(key, variant, out _)`, with the variant passed explicitly, never null |
| Compat dictionaries | Merged into `Application.Resources.MergedDictionaries` for the test that needs them |
| The keys | DiffView's own tokens, and AvaloniaEdit's references less its own definitions, read at test time by the audit's scanners |
| The expected gaps | Two hand-written lists of what AvaloniaEdit's theme files lack under Semi: 6 keys its Fluent files reference, in every variant, and 9 its Simple files reference, 8 in the four high-contrast variants, which define `HighlightColor`. A second test also asserts them from `AuditRunner.Run` |
| The verdict | The keys missing at run time equal the expected gaps exactly, so a new gap fails it and so does one closed; with the compat dictionaries merged, none is missing |

DiffView's check also renders a `TextEditor` under each Semi variant and asserts on some colours.
Both of those are DiffView's own concern, not the audit's.

## Decisions

| 1 | **The check compares the audit's answer with Avalonia's, key by key, for the keys a theme must supply.** It covers each consumer, under each theme the audit reads it with, in each of that theme's audited variants. The keys are those the consumer references and does not define itself. For each key it asks Avalonia, and reports each disagreement, of three kinds. A key the audit calls defined that Avalonia does not find. A key the audit calls undefined that Avalonia does find. And a key whose lookup throws, which carries the exception's message. No disagreement is the pass | The audit's gaps are the keys a theme leaves undefined for a consumer, so those are what the check confirms. A key a consumer defines itself may live in a control's own `Resources`, where no lookup at the application can see it, so checking it would report differences the audit is not wrong about; DiffView's check takes AvaloniaEdit's references less its own definitions for the same reason. A key a theme defines only in a control's own resources, as in a `ControlTheme`'s, is the theme's to the audit and out of the application's reach, so it is reported as the first kind: there the audit's model is wider than the lookup. At 12.1.3 a `ResourceDictionary` builds a deferred entry inside the lookup, so what fails on the lookup's path throws there, an include that does not load or an alias whose target is missing among them, and an uncaught lookup would end the run at the first such key. An alias looks its target up under the variant of the dictionary that holds it, and one outside any variant's dictionary under none, which reads only the `Default` ones |
| 2 | **The gaps and the keys come from the audit's result**, `AuditRunner.Run` in the same test run, and the library works out from it what to look up. ### Dismissed

- **A `Styles` root the check builds for itself, leaving the application alone.** It runs beside any
  test, but it is a second model of where an application holds its theme, by decision 4.
- **Checking the keys a consumer defines itself.** A lookup at the application cannot see a key held
  in a control's own resources, by decision 1. DiffView's own token test stays its own.
- **Gaps taken from the committed report, or from a new JSON output.** The report is Markdown for
  people, and parsing it would make its format a second contract. A new output is a second answer
  beside `AuditRunner.Run`, which a test project can call directly.
- **Variants built from their display names.** That is the inheritance trap, by decision 3.
- **Fluent's, Simple's and Semi's sources read by the tests**, fetched by the build or committed as
  fixtures. Every test run on three operating systems would need the network, or this repository
  would republish other projects' code, by the developer's decision of 2026-10-14.
- **The whole check in the source package, every type internal.** A public test method could not take
  one of its types (CS0051), and logic that needs no running framework would be tested only beside
  Avalonia, by the developer's decision of 2026-10-14.
- **The package as a development-only dependency.** `dotnet add package` then leaves out the library's
  compile assets, by decision 6.
- **A minimum of 2026.3.928, the oldest library that carries the audit's types.** The source half calls
  the library's half, which no earlier release carries, so that pair would not compile.
- **The tests under `tools/`, outside the solution, as the probe is.** They would run only in a step of
  their own, and `dotnet test --solution` would skip them.
- **A test-framework attribute shipped in the package**, such as an `[AvaloniaFact]` that runs the
  check. It would choose the adopting project's runner, which the library never does.
- **Shipping the check as a compiled assembly that references Avalonia.** It would pin an Avalonia
  for every adopting project, and the developer decided against it on 2026-10-13.
- **Adopting Templates' `packages.push` list for the release in the same change.** It is the family's
  convention, but a change to how releases name packages is a concern of its own.
