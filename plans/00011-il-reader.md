# 00011 — An IL reader in AssemblyQuality, and two rules on it

> Status: **approved 2026-11-19**. Supersedes nothing.

The developer asked on 2026-11-19, in AppKit's session, for AssemblyQuality to have an IL reader, "the most feature
rich, rather than the lightest", and picked ICSharpCode.Decompiler 11.2.0.10050 (MIT), over Mono.Cecil and dnlib. The
request reached this repository from that session the same day. Its first consumer is AppKit's `plans/00007`. Step 5
of that plan sweeps the IL of `AppServices.AvaloniaUI` for four things, and it waits for this plan's release.

1. No method constructs an `Avalonia.Controls.Window`, or a subclass of it, that the assembly does not declare.
2. Outside one named type, and the types nested in it, nothing makes a colour or a brush. That covers the constructors,
   the parse and factory methods, and reads of `Colors`, `Brushes` and the internal `KnownColors`.
3. No method but one named helper looks up a resource.
4. Every call to `DialogColors.Brush(string)` passes one of an internal class's `const string` fields. Every one of
   those fields is passed somewhere. A key is followed through ternaries, locals, tuple deconstruction, and parameters
   whose callers pass a constant.

AppKit plants each case as a defect and must see it turn red. Its `plans/00006` runs the same sweeps over
`ScopedEditors.AvaloniaUI`, which moved into AppKit's repository from ScopedEditors' own and fails them today. Among the
failures, `JsonHighlightBlock` holds eight literal brushes.

Cases 3 and 4 are read through an attribute the code carries, by the developer's decision of 2026-11-19: a helper marks
its key parameter with the class its keys come from. AppKit marks `DialogColors.Brush`. ScopedEditors' three
`BrushHelper` methods can be marked once its keys are the constants of a class, which they are not today, and which its
`plans/00006` decides. The release's message to AppKit says both.

AssemblyQuality reads assemblies by reflection and their metadata tables. It reads no method body, and it takes no
package dependency.

## Decisions

| # | Decision | Why |
|---|---|---|
| 1 | **The reader is built on ICSharpCode.Decompiler 11.2.0.10050, pinned in `Directory.Packages.props`.** It reads each method body as the decompiler's ILAst, after the decompiler's own transforms. Those transforms rebuild locals, ternaries, tuple deconstruction, object construction and the compiler's generated methods into one tree per method. Decision 5 names each use as the compiler emits it; step 2 records the form each takes after the transforms, and the reader matches that form | The developer's choice. The package targets `netstandard2.0` and depends only on System.Collections.Immutable and System.Reflection.Metadata 9.0.0, which .NET 10 ships. Case 4's data flow needs the transformed tree. Raw IL spells a ternary as branches, and a value-type construction three ways |
| 2 | **It lives in `Bennewitz.Ninja.AssemblyQuality` itself.** That is the package's first dependency, so every consumer takes the decompiler with it | The developer asked for AssemblyQuality to have an IL reader. Its consumers are test projects, where one more library costs nothing a release can measure |
| 3 | **The key attribute is `Bennewitz.Ninja.ResourceKeyAttribute`, matched by its full name and declared by the consumer.** It goes on a `string` parameter and takes one argument, the class whose `const string` fields are the keys: `Brush([ResourceKey(typeof(DialogColors))] string key)`. No package ships it. A consumer declares it `internal`, once, in the lowest project that needs it, which its friend grants make visible to the rest, in a few lines `docs/assemblyquality.md` gives, as the nullable attributes are declared where the framework lacks them. The docs say why once: two projects that each declare it, one referencing the other, get CS0436, an error under warnings as errors. The key class may be nested, or in an assembly the scanned one references | The code then says which methods are helpers, which argument is the key and where the keys live, and the compiler keeps that true through a rename. AssemblyQuality is a test project's package, so the code it reads cannot reference it, and a match by name is how such an attribute is found. No attribute that exists fits: `ConstantExpected` names no set of keys, and JetBrains' `ValueProvider` is conditional, so the compiler leaves it out of the IL |
| 4 | **Two rules, numbered `BNAQ1010` and `BNAQ1011`.** Each matches types and members by full name, never by a reference, so a rule can name an internal type such as `KnownColors`. `BNAQ1010` takes a list of entries, each naming a type or a member, what counts as a use of it, and where that use is allowed; decision 5 says what each part may be, and step 3's pull request settles the constructor's signature, which is permanent API, and records it in `PROGRESS.md`. `BNAQ1011` takes no configuration, only the attribute. AssemblyQuality takes no Avalonia, and `AvaloniaConfinementTests` holds every project but `tests/XamlQuality.ThemeRuntime.Tests` to the same | Two rules cover AppKit's four cases, and ScopedEditors' with them. A rule per case would name Avalonia in a library that reads WPF and MAUI assemblies as well. A `BNCQ` rule with a `BNAQ` counterpart carries its number, and `BNCQ1007` and `BNCQ1008` have shipped for other things, so the next numbers free in both families are taken. That leaves `BNCQ1011` free for `BNAQ1011`'s counterpart |
| 5 | **`BNAQ1010`, confined use.** Named uses happen only inside named types, their nested types included, or named methods. As an option, by the developer's decision of 2026-11-19, a use may instead be allowed by its key: the entry names which of the member's arguments is the key, as `TryGetResource`'s first or the `FindResource` extension's second, and the use is allowed wherever that argument traces, as decision 6 follows a value, to a parameter that carries the key attribute. An entry says which of these counts as a use of what it names: <ul><li>constructing the type: `newobj`; a `.ctor` called on an address, other than a constructor chaining to its own base or `this`; or `initobj` of a value type;</li><li>any use of the type's members: a call, a delegate made from a method, or a read of a field or a property;</li><li>a use of one named member, as a call, a delegate or a read.</li></ul> So case 1 is constructing `Window`, and `dialog.ShowDialog(window)` is no use; case 2 is constructing `Color` and `IBrush`, any member of `Colors`, `Brushes` and `KnownColors`, and the named parse and factory methods. A type can be matched with every type that derives from it or, for an interface, implements it, directly or through another interface: case 2's `IBrush` is reached by `ImmutableSolidColorBrush`, which implements it and derives from no brush class. A member is matched on the type it is named on and, with that option, on every type the option matches, by name and signature: `TryGetResource` named on `IResourceNode` matches the `Application.TryGetResource` a call through an `Application` binds to. Optionally, types the scanned assembly declares itself are excluded. A constructor chaining to a matched base is no use, and the reading lists it as a chain | Cases 1 to 3. Case 1 is "construct a `Window` subclass the assembly does not declare". A window class chaining to its base constructor is not a construction, and AppKit's positive control is exactly those calls, so the reading shows them. A call holds the member the compiler bound to, which is the class's own where the class declares one: ScopedEditors' `BrushHelper` calls `TryGetResource` through `Application`. Allowing a lookup by its key closes the gap the attribute leaves: a wrapper nobody marked looks up a key no marked parameter gave it, and is reported, and so is a marked helper that looks up a literal. Tracing the key, rather than asking which method holds the lookup, follows a marked helper that hands its key to a private method that looks it up, as ScopedEditors' `BrushHelper.Resolve` hands it to `ColorFor`, and names each key that cannot be traced, as the keys `ColorFor` is given from `BrushHelper`'s refresh dictionary. The library still names no lookup: the consumer's entry does. AppKit's case 3, one named helper, does not rest on the option |
| 6 | **`BNAQ1011`, keys through marked helpers.** Every argument given to a parameter that carries the key attribute must be a constant equal to one of the `const string` fields of the class the attribute names. Every such field must reach some parameter that names its class, somewhere in the scan, followed the same way: `DialogColors.SubtleBrush` reaches `Brush` only through `GlyphButton`'s parameter, and `WarningBrush` only through a ternary of tuples. A value is followed within its method through: <ul><li>locals, each of whose stores is followed;</li><li>ternaries, whose arms are both followed;</li><li>tuple construction and deconstruction;</li><li>a parameter, through every caller in the scan, to a depth of eight.</li></ul> A value from a delegate, a field, or anything else is unknown, and an unknown value is a finding. So is a parameter whose method the scan cannot see every caller of: one that is public or protected, one that overrides or implements another, and one made into a delegate. An internal method stays followed through the scan's callers, though the assembly grants its internals to its tests. A marked helper made into a delegate is a finding too, since no call shows its keys. A marked parameter that is not a `string`; an attribute found by name whose argument is not one `Type`, given to its constructor, that resolves; an attribute whose class has no `const string` field; and two of a class's fields that hold one value are named in `Skipped`. A literal equal to a field's value reads as that field | Case 4. A `const` is compiled into its uses, so a key is matched by value, and a literal that spells a field's value cannot be told from the field: AppKit is told it cannot plant that defect. "Unknown is a finding" keeps the rule from passing a key it could not follow, as AppKit requires. Every marked parameter naming one class is one set, so ScopedEditors' three helpers share their keys |
| 7 | **Every method body is read, including the compiler's.** That means lambdas and their display classes, local functions, async and iterator state machines, static constructors, accessors, and compiled XAML. A use in a generated body is credited to the method the source wrote, named in the compiler's mangled name (`<M>b__`, `<M>g__L\|`, `<M>d__`), so a confinement to a method covers its lambdas. A generated type's plumbing, its constructors, the `<>c` class's static constructor, `SetStateMachine` and an iterator's enumerator members, is credited to the same method. Compiled XAML, the methods whose names begin with `!` and the types named `XamlClosure_`, is credited to the markup it was compiled from, its `x:Class` or, with none, its file, as step 2 measures, and a confinement names it the same way. Other generated code, such as `<PrivateImplementationDetails>`, is read as methods of its own. Only a generated name the reader cannot take apart is named in `Skipped`. A use is known by the method and the IL offset it was compiled at, so a body the transforms fold into its source method, and that is also read on its own, gives one use | Code a lambda holds is the method's code. Charging it to `<>c__DisplayClass` would put a finding where nobody can fix it, and miss a confined use. A generated type always holds methods no transform consumes, so skipping what the transforms leave would make clean code skip. `ScopedEditors.AvaloniaUI`'s `EditorColors.axaml`, which has no `x:Class`, holds 15 hex colours its compiled markup makes |
| 8 | **Each rule has a public reading as well as its findings.** `ConfinedUseRule.Read` returns every matched use and every chain to a matched base: its kind, the method that makes it, where it is in the source, and whether it is allowed. `HelperKeyRule.Read` returns every marked parameter, every call to it and each value that reaches it. `Analyze` derives its findings from the reading, as `TemplatePartRule.ReadParts` does for `BNXQ1003` | A consumer's positive controls are uses the rule allows. Without the reading a consumer cannot see them, and a reader that went blind would look clean. The reader itself stays internal until a third use asks for it |
| 9 | **A finding says where in the source it is, wherever symbols are there.** The reader takes sequence points from a portable PDB, embedded in the DLL or beside it. `AssemblyFinding` gains an `init` property, `Source`, holding the file and line, null with no symbols, and its remark that a finding has no line is rewritten. A finding without symbols names the method and the IL offset | AppKit's Release builds embed their PDBs, and its Debug builds put one beside the DLL. An `init` property adds to a public record without breaking any consumer of it |
| 10 | **`Inspected` and `Skipped` keep AssemblyQuality's contract.** For `BNAQ1010`, `Inspected` is the number of method bodies read in a scan where its configuration names anything, and every type and member it names must resolve, internal ones included, in some assembly of the scan or of what they reference; a name that resolves nowhere is named in `Skipped` once per scan, not once per assembly. For `BNAQ1011`, it is the number of calls to marked parameters, and a scan with no marked parameter inspects nothing. `Skipped` names each of these, and a rule never passes one: <ul><li>an assembly with no file to read;</li><li>a configured name that resolves to nothing;</li><li>a reference that does not resolve from the assembly's folder or the shared framework, where a match depended on it: a base type or an interface followed for a match, or a called member's declaring type;</li><li>a generated name the reader cannot take apart;</li><li>a method body the decompiler cannot read;</li><li>what decision 6 names.</li></ul> | AppKit's tests require an empty `Skipped` and `Inspected` above zero. A misspelt name would otherwise leave `BNAQ1010` inspecting every body and matching nothing, which reads as clean; a misspelt attribute leaves `BNAQ1011` inspecting nothing, which that requirement catches. A reference no match needed is no reason to skip. A matcher gone blind still reads bodies, so `Inspected` cannot catch it: a consumer asserts its positive controls through the reading, and the release's message to AppKit says so |
| 11 | **Both rules are proved on fixture assemblies that stand in for the real cases, and on real code.** Each case gets a compiled fixture under `tests/fixtures/` with types named for it: a window, a colour struct, a brush interface, a lookup helper with a marked parameter, a key class, and each compiler-generated body. The real Avalonia cases are run in scratch, outside the tests, on a copy with the attribute declared and the helpers marked, as AppKit will mark them | AssemblyQuality's tests take no Avalonia, and fixtures are real compiled types, never mocks. Real code is where a stand-in could be wrong |
| 12 | **A mutation set of the reader's and the rules' own, `tests/AssemblyQuality.Tests/Mutations/il.json`**, run with `mutate --swap src/AssemblyQuality/AssemblyQuality.csproj`, as plan 00010 decision 7 did for `BNCQ3002` | Each test must be shown to fail |
| 13 | **The numbering.** This is plan 00011, by the developer's decision of 2026-11-19; the isolation rule's plan becomes 00012, and the compile-time analyzers below become 00013. The plan continues the main sequence, as `plans/AGENTS.md` requires, not `plans/assemblyquality/` | A peer is waiting on this release, and neither of the others blocks anybody |

### Dismissed

- **Mono.Cecil or dnlib.** The developer chose the decompiler.
- **XamlQuality's `CompiledStrings`.** It is internal to another family, it decodes IL by hand, and it has no data flow.
- **`MethodBody.GetILAsByteArray` and a hand-written decoder.** That would cover cases 1 to 3, but not case 4's data
  flow, and the developer asked for the most capable reader.
- **Decompiling to C# and reading the syntax.** Slower, it loses the IL offsets that the sequence points map, and the
  ILAst already holds the structure case 4 needs.
- **A package of its own, `Bennewitz.Ninja.AssemblyQuality.IL`.** It would keep the base package dependency-free, at
  the cost of a second package, a second README and a second id to release, for consumers who are all test projects.
- **A public reader in this release**, which AppKit's request suggested the two rules sit on. Each rule's reading
  serves the controls, and a public reader is permanent surface that neither of AppKit's plans calls.
- **Naming the helpers and the key class in `BNAQ1011`'s configuration.** A rename silently empties it, and
  ScopedEditors' three helpers would need a list that the code already knows.
- **An attribute that already exists.** `ConstantExpected` names no set of keys, and JetBrains' `ValueProvider` never
  reaches the IL.
- **A package that ships the attribute.** The code that carries it is shipped code, which a test package cannot reach,
  and a match by name needs none.

## Scope

**In:**
- the reader;
- `BNAQ1010` and `BNAQ1011`;
- the key attribute's name and contract, and the declaration `docs/assemblyquality.md` gives;
- `AssemblyFinding.Source`, and its remark;
- the decompiler's pin;
- their fixtures, tests and mutation set;
- their sections and the regenerated table in `docs/assemblyquality.md`;
- `PROGRESS.md`, where the renumbering of the isolation rule's plan is recorded.

**Out:**
- AppKit's sweeps, and the attribute on its helpers, which AppKit writes;
- the compile-time analyzers, plan 00013: `BNCQ1011`, `BNAQ1011`'s counterpart, which checks each argument a marked
  parameter is given, and `BNCQ3003`, which reports an Avalonia resource lookup whose key does not come from a marked parameter;
- the isolation rule;
- any rule about Avalonia;
- the release, which happens on the developer's word, followed by a message to AppKit naming the version, the API,
  the attribute its helpers must carry, that its positive controls are asserted through the readings, and that a
  literal equal to a key cannot be told from the key, whose text the developer approves.
